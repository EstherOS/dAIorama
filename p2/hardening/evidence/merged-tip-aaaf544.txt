## [1] Finding (fixed on this branch): the B9 pacing test fails at the merged tip under load
===================================================================
The base tree's gate is red, first suite:

  test runtime::service::tests::control_calls_are_paced_by_the_default_bucket ... FAILED
  panicked: the 41st call was paced: 11.296909ms
  test result: FAILED. 286 passed; 1 failed; 6 ignored

Not a product defect: the bucket refills continuously, so a single call's wait is only what is
left of the current token period (`wait = (1 - tokens) / per_sec`). 11.296909 ms at 20/s means
the bucket held 0.774 tokens when the 41st call arrived — i.e. the 40-call drain itself took
~39 ms under the full-suite load, handing the next call a 0.8-token head start. The assertion
(>= 35 ms) assumes the drain is ~free; it holds on an idle box and fails when the gate container
is loaded. The same test passes 6/6 alone (`-pace`) and 4/4 at `--test-threads=32` (`-repro2`),
so the red run is the loaded case, not a broken tip.

Fix: measure a span instead of one call's remainder — drain the default burst (40), then time
20 further calls; 20 tokens at 50 ms each cost >= 18 periods even after two tokens of refill
(>= 900 ms), asserted at >= 700 ms for margin. A regression that stops pacing (20 calls in tens
of milliseconds) cannot pass it.

test 0 — 17 suites, **447 passed / 0 failed / 6 ignored**, matching the merged ledger for
e07e784. Base-tree log kept as `gate-aaaf544-base-red.log` (rc=101 at the first suite).

                          wait, [F2] no max_wait refusal, [G2] no queue-bound refusal
  history         rc=1   (history-aaaf544.log) — [B1] "six control calls wrote six records" n=0,
                          and the cases built on it

Mechanism (one cause, not five): #117 made the bucket gate skip ids that cannot name a session
and #118 made `session_known` (live registry **or** durable history) gate both pacing and
recording. Every one of these probes drives control calls for **invented** ids (`s-1`,
`s-hist-1`, …) on a bench that cannot create a real session (no compositor in `rust:slim`), so
after the two merges those calls earn no bucket and write no record — by design, and the
merged behavior is what #118 was approved for. The legs need a known-session fixture: seed
`<history>/<id>/seg-00001.jsonl` with one record before the calls (`recorded_scope` reads the
first segment, which makes the id known without creating a session), and filter that seed out
of the record assertions.

Follow-up claimed on the board as `P5-LEG-PROBES-KNOWN-SESSION`. Until it lands, the shipped
pacing and history-recording paths have no live leg at this tip — the two unit suites still
cover them (447 green), and `history-bound` still proves the invented-id refusals.
