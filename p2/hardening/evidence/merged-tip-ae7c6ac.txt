### New leg — C2 release manifest, driven with a real keypair

The unit suite pins `release.rs` against fixture bytes; nothing exercised the trust list the
way an operator does. `p2/hardening/run-release-manifest.sh` generates two throwaway minisign
keys and builds the same `git archive HEAD` tree three times, appending keys to
`packaging/release/trusted-keys` between builds (the trust list is `include_str!`, so "trusts
key X" is a build, not a flag). `probe-release-manifest.py` then drives the shipped binary:

- **Generator:** valid JSON; one artifact object per line and one asset object per line;
  real sha256/size for both artifacts and the asset; `facts.components` derived from the row
  kinds; duplicate basenames refused (`appears twice`); an artifact spec that is not
  `kind:target:path` refused; a missing input file refused.
- **POSIX reader:** every artifact row and the asset row yield name+sha256 through a
  quotes-split, no `jq` — the installer contract from the pre-read.
- **Empty trust list:** refuses with `no trusted release key provisioned` before the
  signature file is even read (measured with a signature that does not exist).
- **Real signature:** a minisign signature over the generated bytes verifies; the printed
  signer id equals the id inside the public key (byte order included); `--json` carries
  version/protocol/key_id and no artifact when none was asked.
- **Artifact matching:** matching file verifies and prints `artifact core <name> sha256 <hex>`;
  a same-name file with one extra byte is refused on the digest; an unknown name is refused
  by name; a listed row whose file is absent is refused on the read.
- **Signature before parse:** an edited manifest reports `release signature verification
  failed` (not a JSON error); a re-signed manifest with `format: 2` reports
  `unsupported release manifest format 2`; a re-signed manifest missing `version` names the
  field; an unparseable signature reports `invalid release signature`.
- **Rotation:** a second key's signature is refused as `release signed by an untrusted key
  <id>` by the key1-only build, and accepted by the key1+key2 build — the outgoing key stays
  accepted in the same build. A client-only manifest (no artifacts) verifies, and asking for
  an artifact against it is refused.
