Rate-limiter bucket-map growth — live leg (P5 hardening)

Tree:   base `75050e8` (spec/v1)  ->  fix: this branch (`p5/rate-bucket-bound`, rebased on `68c01ad`)
Image:  docker.io/library/rust:slim, one fresh container per run; python3 for the probe
Leg:    p2/hardening/run-rate-buckets.sh <binary> <label>
        one real `daiorama serve`, real unix-socket frames into `dispatch()`, repeated
        identical loads, manager VmRSS read from /proc/<pid>/status after a 0.6 s settle.
        Every id here is longer than the store's 128-byte session-id bound, so every call is
        answered `session_not_found` — the frame is accepted, the rate gate runs, nothing else
        does. That isolates the bucket map from session work and from history writes.

Finding (base): the B9 bucket map is keyed by the caller-supplied `session_id` and never
shrinks. `dispatch()` spends the control-class token before any session lookup, so a call
naming nothing still inserts `"<scope>:<id>"` verbatim. Measured: each round of 16 calls
carrying 1 MiB ids added ~17 MB to VmRSS and the next round added another ~17 MB (linear, not
allocator noise); one 6 MiB id added ~17 MB on its own; twelve 6 MiB ids added ~100 MB total
and the process never released it. A client that can send control calls can therefore grow the
manager without bound until every session on the box dies with it.

Fix (this branch): ids that cannot name a session are never keyed (the handler already answers
`session_not_found`; nothing is refused differently); the map is capped at 4,096 buckets with
the least-recently-used quarter evicted on overflow (never a bucket with a caller parked on
its gate); `close_session` drops the bucket for the closing and the creating scope.

== reading
- [B] rounds 2 and 3 add exactly 0 kB on the fix; on the base they add 16,384 kB and 17,408 kB.
  Round 1's growth on the fix (~7-8 MB) is allocator arena for the 1 MiB frames, not the map:
  it does not repeat.
- [C] twelve 6 MiB ids: base 103,428 kB total, climbing on most calls; fix 36,856 kB total in
  three arena-sized jumps (11.3 / 13.3 / 12.3 MB, frame buffers) with zero on every other call
  and a 54,808 kB peak. The fix's share is allocator arena, not map entries — the map never sees
  these ids at all.
- [D] both builds keep pacing (burst 2 reject, third call `rate_limited` with a retry hint), and
  every id in [B]/[C] is answered `session_not_found`, so refusal behaviour is unchanged.
- Residual, same class and not fixed here: `History` keeps an in-memory per-session map and a
  session directory for a `tool.call` record naming a valid-but-unknown session id. Both are
  keyed by client input too; the rate map was the sharpest (arbitrary key bytes retained with
  no cleanup at all). Named for a follow-up, not scored in this leg.
